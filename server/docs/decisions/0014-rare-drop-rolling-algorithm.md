# 0014. Rare-drop rolling algorithm

## Status
Accepted (implements the rare-drop-rolling logic left open by [0012](0012-item-catalog-model.md), crediting into [0013](0013-character-inventory-ownership-model.md)'s `character_inventory`)

## Context
[0009](0009-tracking-offline-progress.md) established that a character's randomized primary reward yield is approximated as a single draw from a Normal distribution (via the Central Limit Theorem) rather than looping `n` individual draws, since an offline character can accumulate a very large `n` and looping that many random draws would be needlessly expensive. That approximation is appropriate there because the underlying per-action draw is a continuous-ish uniform range with a reasonably large expected value.

`game.action_rare_drop` ([0010](0010-action-and-rare-drop-model.md)) is structurally different: each row is an independent, typically low-probability Bernoulli event, not a continuous range. The Normal approximation breaks down badly for rare events at realistic `n`. For example, at `n = 1` and `drop_chance = 0.01`, the true distribution is "1% chance of exactly 1, 99% chance of 0," but a Normal approximation centered at mean `0.01` with a correspondingly tiny standard deviation would round to `0` in effectively every case — silently turning a real 1% chance into an effective 0%. This inaccuracy gets worse, not better, as drop chance shrinks or `n` stays small, and rare drops are specifically designed to have low `drop_chance` values, so this is the common case the approximation would mishandle, not an edge case. There is also no statistics library in the project beyond `java.util.Random` (no Apache Commons Math or equivalent in `pom.xml`), so an exact closed-form binomial shortcut isn't readily available either.

An action can define any number of `action_rare_drop` rows, and they are independent of one another, not mutually exclusive — multiple different items can drop from evaluating the same action over the same elapsed time.

## Decision
Roll rare drops via exact per-tick Bernoulli simulation instead of a distributional approximation: for every `ActionRareDrop` row belonging to the character's current action, loop `n` independent trials (`random.nextDouble() < dropChance.doubleValue()`), count successes, and credit that count directly into `game.character_inventory` using the find-or-create semantics from [0013](0013-character-inventory-ownership-model.md). Rows with zero successes are skipped entirely — no read or write is attempted — both because there's nothing to credit and because attempting to persist a zero-quantity row would violate `character_inventory`'s `CHECK (quantity > 0)` constraint.

This is implemented as a private `rollRareDrops(character, action, n)` helper on `PlayerCharacterService`, called once per `calculateOfflineProgress` invocation, after the primary-reward block. The helper is deliberately kept decoupled from offline-progress-specific bookkeeping — it never reads or writes `last_calculated_at` — so it can later be reused as-is to resolve rare drops for a single completed action instantly (`n = 1`), if a non-offline, immediate-resolution action path is ever added; `n = 1` is simply the smallest valid input to the same loop, not a special case.

## Consequences
Rare-drop outcomes are always statistically exact, with no risk of a low-probability event effectively rounding down to impossible the way the Normal approximation would. This introduces the first `O(n)` component into `calculateOfflineProgress`, which is otherwise `O(1)` in `n` (XP and primary reward are both closed-form expressions) — an outer loop over however many rare-drop rows the action defines, each running `n` trials. This is judged acceptable at realistic scale: even an extreme case of six months offline at a five-second action interval with ten rare-drop rows on the action is on the order of tens of millions of cheap `double` comparisons, sub-second in practice. This should be revisited if the configurable action interval or any offline-duration limit ever changes enough to push `n` far higher.

Primary reward continues to use the Normal-distribution approximation from [0009](0009-tracking-offline-progress.md) unchanged — the two mechanisms are intentionally allowed to diverge, since they solve different statistical problems (a continuous range vs. a rare Bernoulli event), not because of an oversight.
